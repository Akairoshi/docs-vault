# ADR-0001: Использование Clean Architecture в качестве архитектурного паттерна

- **Дата:** 2026-05-16
- **Статус:** Accepted
- **Автор:** —

---

## Контекст

Проект — веб-приложение на ASP.NET Core с планами расширения на Android-клиент.
Нам нужна архитектура, которая:

- отделяет бизнес-логику от инфраструктуры (БД, HTTP, внешние сервисы)
- позволяет тестировать бизнес-логику без поднятия ASP.NET или БД
- не привязывает приложение к конкретному фреймворку или ORM
- масштабируется по мере роста проекта

---

## Решение

Мы используем **Clean Architecture** (по Robert C. Martin) с разделением на слои:

```
src/
├── Domain/          ← сущности, value objects, доменные исключения
├── Application/     ← use cases, интерфейсы репозиториев, DTO, маппинг
├── Infrastructure/  ← EF Core, внешние API, реализации репозиториев
└── WebApi/          ← контроллеры, middleware, DI-конфигурация
```

Правило зависимостей: **каждый слой зависит только от слоёв внутри себя**. `Domain` не знает ни о чём. `Application` знает только о `Domain`. `Infrastructure` и `WebApi` знают обо всех.

---

## Рассмотренные альтернативы

### Вариант A: Стандартный MVC (Controllers → Services → Repositories)

**Плюсы:**
- Прост для старта
- Хорошо знаком большинству .NET разработчиков

**Минусы:**
- Быстро превращается в «сервисы на тысячу строк»
- Бизнес-логика смешивается с инфраструктурными деталями
- Тяжело тестировать без поднятия всего стека

**Причина отказа:** Не подходит при планируемом росте проекта.

---

### Вариант B: Вертикальные слайсы (Vertical Slice Architecture)

**Плюсы:**
- Каждая фича полностью изолирована
- Нет общих абстракций, которые тянут за собой

**Минусы:**
- Сложнее при сильно связанной доменной модели
- Меньше структуры, выше риск дублирования

**Причина отказа:** Менее подходит для приложений с богатой доменной логикой.

---

## Последствия

### Положительные
- Бизнес-логика полностью изолирована и тестируема
- Смена ORM или транспорта не затрагивает `Application` и `Domain`
- Чёткие границы ответственности для каждого слоя

### Отрицательные / Компромиссы
- Больше проектов в Solution с самого начала
- Требует дисциплины — легко случайно нарушить направление зависимостей
- Некоторые простые CRUD-операции требуют больше кода, чем в MVC

### Нейтральные / Заметки
- Для валидации команд используем FluentValidation в слое `Application`
- Для маппинга DTO ↔ сущности используем AutoMapper или ручной маппинг — отдельное решение (см. ADR-0002)

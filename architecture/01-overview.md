# Что такое архитектура

### Определение

Архитектура программного обеспечения — это набор фундаментальных решений о том, **как структурирована система**: из каких частей она состоит, как эти части взаимодействуют, и какие ограничения действуют на их взаимодействие.

Архитектура отвечает на вопросы:
- Как разделить систему на части?
- Как эти части будут общаться?
- Где живёт бизнес-логика?
- Как система будет меняться со временем?

### Зачем она нужна

Без осознанной архитектуры проект неизбежно приходит к состоянию, которое называют **Big Ball of Mud** — всё зависит от всего, изменения в одном месте ломают другое, новый разработчик не может разобраться, где что находится.

Хорошая архитектура:
- делает код **предсказуемым** — понятно, куда добавлять новую функцию
- снижает **стоимость изменений** — замена одного компонента не ломает остальные
- упрощает **тестирование** — компоненты можно проверять изолированно
- облегчает **онбординг** — новый человек быстро понимает структуру

### Архитектура vs Дизайн

Часто эти понятия путают.

| | Архитектура | Дизайн (Design) |
|---|---|---|
| Уровень | Система в целом | Отдельные компоненты |
| Примеры | Монолит vs микросервисы, Clean Architecture | Паттерн Repository, DI, SOLID |
| Когда меняется | Редко, дорого | Чаще, дешевле |

На практике граница размытая. Главное: **архитектурные решения трудно обратить**.

### Ключевые свойства хорошей архитектуры

**Separation of Concerns (SoC)** — каждая часть системы отвечает за одно.

**Low Coupling** — компоненты слабо зависят друг от друга. Изменение одного не тянет за собой другие.

**High Cohesion** — внутри одного компонента всё связано по смыслу. Не бывает класса «утилиты» куда скидывают всё подряд.

**Dependency Inversion** — модули верхнего уровня не зависят от модулей нижнего уровня напрямую. Оба зависят от абстракций (интерфейсов).

Пример на C#:

```csharp
// Плохо: UserService напрямую зависит от SqlUserRepository
public class UserService
{
    private readonly SqlUserRepository _repo = new SqlUserRepository();
}

// Хорошо: UserService зависит от интерфейса
public class UserService
{
    private readonly IUserRepository _repo;

    public UserService(IUserRepository repo)
    {
        _repo = repo;
    }
}
```

Теперь `UserService` не знает, где хранятся данные — в SQL, файле или in-memory. Реализацию можно подменить без изменения самого сервиса.

### Для одного / для команды

**Один разработчик:**
Архитектура всё равно нужна. Даже если ты единственный, кто работает с кодом — через полгода ты уже «другой человек» и не помнишь, почему принял то или иное решение. Фиксируй решения в ADR.

**Несколько разработчиков:**
Архитектура становится общим языком. Без неё у каждого разработчика своя картина системы, и они расходятся.

**Команда:**
Архитектура — это контракт. Он определяет границы, в которых каждый работает независимо, не мешая другим. Без него команда превращается в источник конфликтов и регрессий.

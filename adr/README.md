# Architecture Decision Records (ADR)

## Что такое ADR?

**Architecture Decision Record** — это короткий документ, фиксирующий одно архитектурное решение: что именно было решено, почему, какие были альтернативы и каковы последствия.

ADR решает главную проблему проектов: **со временем команда забывает, почему всё сделано именно так**. Новый разработчик смотрит на код и думает «зачем здесь JWT, а не сессии?» — и либо тратит часы на выяснение, либо меняет без понимания контекста.

---

## Когда писать ADR?

Пиши ADR каждый раз, когда принимаешь решение, которое:

- **трудно обратить** (выбор СУБД, фреймворка, способа аутентификации)
- **неочевидно** для нового человека в команде
- **было предметом обсуждения** — значит, у решения есть нетривиальный контекст
- **влияет на структуру** проекта или другие части системы

Примеры поводов для ADR в .NET/ASP.NET проекте:

| Ситуация | Пример |
|---|---|
| Выбор архитектуры | Clean Architecture vs MVC |
| Выбор ORM | EF Core vs Dapper |
| Аутентификация | JWT vs Cookie Sessions |
| Хранение конфига | appsettings.json vs Vault |
| Коммуникация сервисов | REST vs gRPC |
| Паттерн доступа к данным | Repository vs прямой DbContext |

## Жизненный цикл ADR

Каждый ADR имеет **статус**, который меняется со временем:

```
Proposed → Accepted → Deprecated / Superseded
                ↑
           (или Rejected)
```

| Статус | Значение |
|---|---|
| `Proposed` | Решение обсуждается |
| `Accepted` | Принято и действует |
| `Deprecated` | Устарело, но не заменено |
| `Superseded by ADR-NNN` | Заменено новым решением |
| `Rejected` | Рассматривалось, но отклонено |

> **Важно:** ADR никогда не удаляются и не переписываются задним числом. Если решение изменилось — старый ADR помечается как `Superseded`, и создаётся новый.

## Структура файлов

```
docs-vault/
└── adr/
    ├── README.md             ← этот файл
    ├── template.md           ← шаблон для новых ADR
    ├── ADR-0001-название.md
    ├── ADR-0002-название.md
    └── ...
```

### Правила именования файлов

- Формат: `ADR-NNNN-краткое-описание.md`
- Номер — четырёхзначный, с ведущими нулями: `0001`, `0002`, ...
- Описание — строчные буквы, слова через дефис
- Примеры:
  - `ADR-0001-выбор-orm.md`
  - `ADR-0002-аутентификация-jwt.md`
  - `ADR-0003-clean-architecture.md`

## Процесс написания ADR

### Шаг 1 — Определи контекст
Что происходит в проекте, что потребовало этого решения? Какие ограничения есть (время, бюджет, команда, совместимость)?

### Шаг 2 — Сформулируй решение
Одним чётким предложением: «Мы будем использовать X для Y».

### Шаг 3 — Опиши альтернативы
Что рассматривалось? Почему не выбрали? Это самая ценная часть — именно здесь хранится знание, которое иначе теряется.

### Шаг 4 — Зафиксируй последствия
Что теперь становится проще? Что усложняется? Какие новые ограничения появляются?

---

## Советы

- **Пиши коротко.** ADR — не диссертация. Цель — одна страница.
- **Пиши в момент принятия решения**, пока контекст свежий.
- **Не бойся писать об отклонённых решениях** — `Rejected` ADR тоже ценны.
- **Один ADR — одно решение.** Не смешивай несколько тем.
- **Ссылайся** на связанные ADR по номеру.

# Монолит, модульный монолит, микросервисы

### Монолит (Monolith)

Всё приложение — один деплойный артефакт. Единая кодовая база, единый процесс, единая база данных.

```
┌────────────────────────────────────┐
│           Web Application          │
│  ┌──────────┐  ┌────────────────┐  │
│  │   Users  │  │  Announcements │  │
│  └──────────┘  └────────────────┘  │
│  ┌──────────┐  ┌────────────────┐  │
│  │  Orders  │  │   Payments     │  │
│  └──────────┘  └────────────────┘  │
└────────────────────────────────────┘
              │
        ┌─────▼─────┐
        │    DB     │
        └───────────┘
```

**Когда подходит:**
- Старт проекта
- Команда до 5–7 человек
- Домен ещё не полностью понят
- Нет требований к независимому масштабированию частей

**Плюсы:**
- Прост в разработке и деплое
- Нет сетевых вызовов между частями — всё в одном процессе
- Легко рефакторить границы, пока они ещё не зафиксированы в API

**Минусы:**
- При росте — сложно ориентироваться в коде
- Деплой всего при изменении любой части
- Масштабировать можно только целиком

**Типичная ошибка:** называть монолит «плохой архитектурой». Монолит — правильный выбор на старте большинства проектов.

### Модульный монолит (Modular Monolith)

Один деплойный артефакт, но код строго разделён на **независимые модули** с явными границами и публичными API между ними.

```
┌────────────────────────────────────────────┐
│              Web Application               │
│  ┌────────────────┐  ┌──────────────────┐  │
│  │  Users Module  │  │ Orders Module    │  │
│  │  (internal)    │  │ (internal)       │  │
│  │  Public API ───┼──┼──▶              │  │
│  └────────────────┘  └──────────────────┘  │
└────────────────────────────────────────────┘
                    │
             ┌──────▼──────┐
             │     DB      │
             └─────────────┘
```

Модули не вызывают друг друга напрямую по внутренним классам — только через публичные интерфейсы или события.

Пример структуры проекта:

```
src/
├── Modules/
│   ├── Users/
│   │   ├── Users.Api/          ← публичный контракт модуля
│   │   ├── Users.Application/
│   │   ├── Users.Domain/
│   │   └── Users.Infrastructure/
│   ├── Orders/
│   │   ├── Orders.Api/
│   │   ├── Orders.Application/
│   │   └── ...
└── Host/                       ← точка входа, собирает все модули
```

**Когда подходит:**
- Монолит начал расти, нужны чёткие границы
- Команда 5–15 человек, группы работают над разными доменами
- Хочется подготовить почву для возможного перехода на микросервисы

**Плюсы:**
- Деплой остаётся простым
- Границы явные — случайные зависимости исключены компилятором
- Легко перейти к микросервисам, если понадобится

**Минусы:**
- Требует дисциплины: легко нарушить границы
- Чуть больше бойлерплейта на старте

### Микросервисы (Microservices)

Каждый сервис — отдельный деплойный артефакт, отдельный процесс, часто отдельная база данных. Сервисы общаются по сети (HTTP/REST, gRPC, очереди сообщений).

```
┌──────────┐   HTTP    ┌──────────┐
│  Users   │──────────▶│  Orders  │
│ Service  │           │ Service  │
└────┬─────┘           └────┬─────┘
     │                      │
┌────▼─────┐         ┌──────▼─────┐
│  Users   │         │   Orders   │
│    DB    │         │     DB     │
└──────────┘         └────────────┘
```

**Когда подходит:**
- Разные части системы требуют независимого масштабирования
- Команды полностью независимы (Conway's Law)
- Разные требования к технологиям для разных частей
- Зрелая инфраструктура (CI/CD, Kubernetes, мониторинг)

**Плюсы:**
- Независимый деплой каждого сервиса
- Независимое масштабирование
- Технологическая свобода

**Минусы:**
- Сетевые вызовы вместо вызовов функций — задержки, ошибки сети
- Распределённые транзакции — сложно поддерживать консистентность
- Нужна серьёзная инфраструктура
- Сложная отладка и трассировка

**Типичная ошибка:** начинать с микросервисов. Большинство команд не готовы к операционной нагрузке. Начни с монолита или модульного монолита.

### Сравнительная таблица

| | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Сложность деплоя | Низкая | Низкая | Высокая |
| Сложность разработки | Низкая (поначалу) | Средняя | Высокая |
| Масштабирование | Целиком | Целиком | По частям |
| Изоляция команд | Нет | Частичная | Полная |
| Подходит для старта | ✅ | ✅ | ❌ |
